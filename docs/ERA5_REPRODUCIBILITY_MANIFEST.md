## Missing information — do not infer

The `pyproject.toml` constraints do **not** establish exact installed package versions. The workflow does not pin all transitive dependencies. The file fetch routine does not write a SHA-256 hash or version of the underlying Zarr object. Neither the GitHub Actions run identifier nor a green test alone establishes the checksum of each NetCDF input.

For a publication-grade reproducible release, capture with an independent workflow or in a controlled rerun:

- exact package versions (`python -m pip freeze`), Python interpreter and platform details;
- input NetCDF SHA-256 hash and coordinate/time metadata;
- source object provenance and retrieved-at time;
- a stable archival identifier or release artifact for numeric outputs.

## Interpretation of the new provenance-only rerun

[Provenance workflow #41288894933](https://github.com/ys30/Western-US-Weather-JAX/actions/runs/41288894933) was initiated to capture `pip-freeze.txt` and a local NetCDF SHA-256/coordinate manifest **without training**. Until its artifact upload completes successfully, no checksum or resolved-dependency values from this run are accepted in the paper.

**Important distinction:** a SHA-256 generated by a fresh 2019–2022 download identifies the *newly retrieved* input file. It must not automatically be presented as the checksum of the files used by historical successful training runs. Different NetCDF serialization, package versions, or source-object updates can produce different hashes even if the selected physical fields are scientifically equivalent. Link any newly generated manifest to its own workflow run and head commit; if exact historical-byte reproducibility is claimed, independently archive and hash the historical training input itself.
